我在公司已有一个可视化的拖拉拽数据处理平台上做了一个能用自然语言搭建和修改管道的智能体。
画布上包含选择列、UNION、JOIN、SQL 脚本等常用算子，用户可以通过连线搭建数据处理流程。
但用户仍需要理解节点语义和参数，经常需要和工程师沟通。
因此团队决定引入Agent层，
使用户能够通过自然语言进行交互，进一步降低使用门槛和迭代成本。

整个 Agent 框架包括两部分：
第一部分使用开源的 Agent 框架 opencode 帮助我们管理上下文，同时接入自定义 API 接口，实现意图识别、对话回滚、远端平台状态同步、和取消任务。

第二部分使用 LangGraph 构造自然语言到可执行 JSON 的子智能体，主要架构为 planner → scheduler → worker → reducer → scheduler/planner。其中 planner 负责选择需要的表格以缩短上下文长度，判断需要构造还是修改 DAG，然后生成 DAG；scheduler 按照拓扑顺序将 task 分配给 worker；worker 负责模型调用、工具执行、校验、提交、重试，
包括一些细节优化，比如字段名自动纠错、候选字段提示等。
我还构建了一套自动化评测体系，用 LLM-as-Judge 替代人工，能够持续、大规模地评估生成质量。


7. 评估怎么做的：
我们的agent会把用户的自然语言需求转换成 JSON DAG 再交给下游执行，但缺一个系统性的验证方式——生成的JSON 到底对不对，只能靠业务人员帮忙核查，没办法规模化。所以我用 LLM-as-Judge 替代人工，能够持续、大规模地评估生成质量。
核心设计上，我将其分成两层。第一层是判定层，用 outcome 作为主判据：把生成的 JSON 传回平台真实执行，拿到最终数据集，再让 judge把执行结果和用户的原始需求做比对，判断任务有没有真正完成。
第二层是诊断层，只在 outcome 判定失败时触发。我会把 DAG 拆开做归因：节点层逐节点判定算子类型选对没有、内容是否符合它声明的 intent；结构层判断整体拓扑是否符合用户需求。这样每个失败案例都能落到一个明确的错误类别里。
最终发现约8成的错误在sql脚本节点，其余错误发生在其他节点和DAG的规划上。
这对于后续训练数据和约束机制的针对性优化有指导作用

(precision 	0.88  Recall 0.90  F1 0.90 macroF1 83%)

SFT和GRPO训练

SFT
接下来是对第一个项目的瓶颈做优化。我们发70%到80%的失败都集中在sql脚本节点，其余30%则在DAG的规划和其他算子的节点。所以我单独针对sql脚本这个子任务微调了一个qwen14b模型替代原来的deepseek v4，显著提升了这个节点的生产准确率和整体执行效率。

UAT刚上线，业务数据还不够，为了做SFT和GRPO管道，我选择了spider benchmark结合huggingface上gold sql和prompt+schema的成对数据。这样我们就有了prompt和true label。支撑了后续稳定训练，方便对比不同策略的效果。
SFT部分我们是直接去拟合gold sql。

为了避免过拟合和保持模型的通用性，我采用lora 添加到 q k v权重矩阵, 以及前馈网络的gate, up, down矩阵，并只跑了1-2个epoch。

因为sql子agent包含重写步骤，不是单轮输出，控制lora容量、学习率等变量恒定的情况下，我对比了不同比例的轨迹监督和单轮监督的混合数据，观察执行准确率。
最后发现 gold SQL（结果监督）与 trajectory supervision（过程监督）的最佳混合比例在1:1 到2：1之间。
最终采用的是2：1的数据混合比例。

SFT过程中，在5e-5的学习率配置下，我发现末端loss较早进入平台期。
因此我尝试了调低学习率，同时尝试了更大的lora容量，做网格搜索。
发现最优组合5e-5的，r=32 alpha=64的配置下，在测试集任务执行上能达到80%的准确率。

2.GRPO
GRPO部分的数据仍然采用spider benchmark数据集。
将执行结果与gold sql执行结果比较，任意列的排列一致即算正确，最终奖励设为1。

我对比了两种采样策略，链式GRPO和树状GRPO
链式，就是每次给定一个提示词。让agent完整跑完一条轨迹，再根据最终执行结果给奖励。
树状的做法是在每个节点做有限的分支探索，用beam search保留两个以内的表现更好的分支继续往下执行，这样可以控制算力的同时多探索一些可能性。

我担心链式在可比性上的局限。...

链式的奖励计算为从末端向前传播的折扣奖励，树状则对所有子节点的奖励求平均再计算折扣。
另外，我也尝试在链式和树状里加入可执行的回退奖励，在组内无方差时用来补充训练信号,
但发现它对逻辑正确率提升有限，甚至略有下降。

另外，我还对一些列超参数做了网格搜索。
最终发现 KL 0.01 1个epoch 温度1.0 gamma0.9是最优的。基于稀疏奖励的链式和树状GRPO执行准确率接近，都在83%左右。

*DAG
UAT 环境上线后收集到少量真实用户需求（200 个原始 task 180 train 20 test），基于此构建 Planner 蒸馏数据：通过 DeepSeek V4 对每个 task 生成 4 条候选轨迹（Best-of-4，共 800 条 JSON），对轨迹结果进行评估。筛选置信度在 0.75-0.9 区间的候选进行人工复核（共计130 条），构建高质量 SFT 训练集。仅针对 task→DAG 这一步骤对 Qwen2.5-Coder-14B + LoRA 进行指令微调，随后以最终执行反馈分数作为 reward 进行 outcome-level GRPO 训练。将 Planner 替换为微调后的 14B + LoRA 模型后，在测试集上 Judge 通过率达 85%。



在GRPO训练阶段，我对训练效率进行了系统性的拆解和优化：
1.
在权重同步阶段，我发现时间异常，每次同步需要40多秒，而lora模块参数只有0.6GB左右。
vLLM中的训练部分依赖于pytorch和fsdp，而fsdp将模块参数重命名导致PEFT找不到只包含lora参数的模块，所以回退到all gather全部权重。
为了解决该问题，我通过monkey patch打补丁为lora模块参数重命名，这样PEFT可以找到lora参数从而大大降低权重同步时间。
把同步耗时从44s降低到6s。


2.
我还通过分层消融，定位到策略更新阶段的瓶颈：
先扩 micro-batch，再用去 padding + 动态批处理消除 padding 浪费，最后放宽 token cap 提升整体吞吐。提升token cap 至32768单位效率不再改善说明算力基本饱和。
最终单步耗时从 62.4s 降到 32.0s，吞吐量从 43.2 token/s 提升到 116.8（约 2.7 倍）。

3. batch size=4 n= 8的时候H100 OOM，堵塞了训练，导致无法扩大batch。
vLLM唤醒阶段 actor仍占用大量显存。通过打补丁调用empty cache()，使得权重同步到vLLM后 actor立刻释放显存。

4.针对推理侧：
为确定 SQL subagent 在 4×H100 上的最优 vLLM serving 拓扑,我在固定请求集(300 条 validation prompt)、固定全局并发(=8)和统一 vLLM 配置下,做了两组对照实验:一是单实例 TP 扩展性(TP=1/2/4),二是固定 4-GPU 总预算下的拓扑对比(4×TP=1、2×TP=2、1×TP=4)。

结果显示,在当前低并发的 workload 下,单实例 TP=4 是最优拓扑:相同四卡预算下,1×TP=4 相比 4×TP=1 将请求吞吐和输出 token 吞吐均提升约 61.7%,p50/p95 延迟分别降低 38.7%/39.5%。

1.可能的问题：你了解opencode的上下文管理机制吗，
opencode管理上下文通常是将上下文分为原版保存的历史对话记录和模型上下文。
每当触发输入长度阈值的时候，模型会根据已有的摘要和 剔除尾部之后的原文生成新的摘要。尾部原文则全部在裁剪过长的工具调用记录后全部保留

2.可能的问题："reducer 具体做什么？和 scheduler 是什么关系？"
reducer 负责收敛 worker 的执行结果：判断某个节点的修改是否影响了下游其他节点（比如字段被删除或类型变了），如果有影响，会把这个失败/冲突信息聚合后交还给 scheduler，触发相关下游节点的重新校验或重试；如果多次重试仍失败，才会升级给 planner 重新判断（比如触发 replan 或降级到全量重建）。

3.可能的问题："worker 内部的事务模型是怎样的，如果校验失败会发生什么？"
worker 对节点的修改先作用在一个 candidate schema 上，不直接改动主流程状态；只有经过校验（比如 SQL 节点会用 Spark 做预校验、推断输出 schema）通过后才提交。如果校验失败，这一批改动会整体回滚，不会污染其他已经成功的节点。

4.可能的问题："scheduler 怎么保证并行执行 worker 时不会互相冲突？"
依赖 topological order 保证有依赖关系的节点不会被同时分配给不同 worker；没有依赖关系的节点并行执行时，各自在自己的 candidate schema 上操作，最后提交时统一做一次一致性校验，出现冲突交给 reducer 处理。

5.可能的问题："planner 判断'构造还是修改 DAG'的依据是什么？会不会判断错误？"
主要依据当前是否已有旧的 DAG/ETL plan：没有旧 plan 走全量构造，有旧 plan 时只做一次分类判断（比如是纯参数修改、结构调整还是需要重构）。为了避免反复横跳导致系统不收敛，这个判断只在流程开始时做一次，后续循环不会重复判断，只允许在修改失败或无效时单向退化到重构。

6.可能的问题："任务取消是怎么实现的？取消之后 worker 正在执行的任务怎么处理？"
这个问题需要你结合实际实现回答（比如是否是通过共享状态标记 + worker 轮询检测取消信号，还是通过中断 API 调用），如果目前设计里这块细节还没想清楚，建议提前理一下，因为这是面试官比较容易追问的"边界情况"类问题。
