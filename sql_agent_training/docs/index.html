Qwen2.5-Coder-14B-Instruct · Pure SFT vs. Mixed SFT

单轮监督与轨迹混合监督的对照实验

实验记录

摘要

本研究比较从同一原始 Qwen2.5-Coder-14B-Instruct 出发的参数高效监督微调策略，并重点考察执行验证轨迹在 SQL agent 协议中的作用。第一步直接比较 Pure-SFT 与 Mixed-SFT：在同一组 500 条 Spider validation 样本上，Pure-SFT checkpoint-300 的 execution accuracy 为 77.60%，Mixed-SFT checkpoint-300 为 80.60%，绝对差异为 +3.00 个百分点。第二步固定 Mixed-SFT 数据，进行学习率与 LoRA rank 网格；lr=5e-5, r=32 仍为最高点估计，扩大到 r=64 未带来稳定收益。第三步固定 lr=5e-5, r=32、4,800 条训练记录与 300 optimizer steps，比较 gold SQL 与 trajectory supervision 的比例；3,200 gold + 1,600 trajectory 取得最高 execution accuracy 79.80%，相对 4,800 gold-only 的 76.40% 提高 +3.40 个百分点。整体结果支持在单轮 gold SQL 监督中混入约三分之一执行验证轨迹，但现有结论仍基于单一训练 seed 与 500-sample validation subset。

研究问题

本实验旨在回答三个问题。第一，在 SQL agent 的执行反馈评测协议下，相较于仅使用单轮 question/schema-to-SQL 样本的 Pure-SFT，引入经执行验证的 trajectory supervision 是否能够在控制模型起点、LoRA 容量、学习率、训练预算与解码协议后带来可观测的 execution accuracy 增益。第二，在 Mixed-SFT 已显示正向点估计后，学习率与 LoRA rank 的有限网格是否改变主候选配置。第三，在固定总训练记录数与优化预算的条件下，gold SQL 与 trajectory supervision 的混合比例如何影响最终执行正确率、rewrite 行为与耗尽交互轮数的比例。

1. 第一步：Pure-SFT 与 Mixed-SFT 对照

第一步检验的核心假设是：在相同原始 14B 起点、LoRA 容量、学习率、global batch size 与 300-step 训练预算下，以经执行验证的 agent trajectory 替换一部分单轮 gold SQL，能否提高模型在多轮执行反馈协议下的最终 SQL 正确率。原始 14B 无 LoRA 模型仅用于刻画微调前性能；第一步的主要效应量定义为 Mixed-SFT checkpoint-300 与 Pure-SFT checkpoint-300 的配对 execution-accuracy 差异。

在相同训练预算下，Mixed-SFT 的 execution accuracy 为 80.60%，比 Pure-SFT 高 3.00 个百分点。训练过程中的最高中间评测结果为 81.00%，与最终结果仅相差 2/500 个样本，因此不作为更换最终模型的依据。

后续实验统一采用完成预设训练预算的 Mixed-SFT 模型。当前结果来自单一训练 seed 和 500 条 validation 样本，尚不足以区分 direct 与 rewrite trajectory 的独立贡献。

3.4 SFT 结论

SFT 实验整体结论如下。第一，Mixed-SFT 相对于 Pure-SFT 的点估计提升在两个独立设置中复现：第一步的 3,200 gold + 1,600 trajectory 为 80.60%，第三步同等比例在重新生成轨迹池后为 79.80%，均高于对应 gold-only 对照。第二，lr=5e-5, r=32 是当前最优且更简洁的 LoRA 配置，r=64 未显示必要性。第三，在固定总训练记录数时，约三分之一 trajectory supervision 是当前最佳比例；它比纯 gold-only 更好，同时比 50% trajectory 更稳定地降低平均交互轮数和耗尽轮数率。

Qwen2.5-Coder-14B-Instruct-SFT-Merged

GRPO 奖励方案与搜索策略实验结果

实验记录

摘要

本实验研究的是两阶段参数高效训练：首先将 Qwen2.5-Coder-14B-Instruct 的 SFT LoRA 合并进 14B 基座，形成统一的 SFT-Merged policy；随后在该 policy 上为每个 GRPO 方案训练一套新的 LoRA，而不是更新 14B 全部参数。初始 S1–S4 reward 设计对照中，S3 的执行准确率点估计最高，为 80.67%，相对 SFT-Merged baseline 提升 3.33 个百分点；随后的超参数实验确定 KL=0.01、PPO epoch=2、temperature=1.0 与 gamma=0.9。在更新后的 SFT ratio base 上，rollout 对照得到 S3 branch=4/beam=2/n=20 83.67%、S1 n=8 83.33% 和 S3 branch=8/beam=1/n=24 82.00%；准确率没有拉开清晰差距，但 S1 n=8 的计算与交互效率最好。

研究问题

本实验旨在回答：在相同 SFT-Merged base policy 与相同第二阶段 LoRA 训练框架下，不同 reward 设计与 rollout 搜索策略是否能够相对 SFT-Merged baseline 提供额外的 execution accuracy 增益；同时，S1–S4 之间的差异应如何在 reward 变量、chain/tree rollout 形式、batch size 与 PPO mini-batch size 等潜在混杂因素共同存在的条件下进行解释。

1. 方法

本节描述 GRPO 实验的比较对象、控制变量与评测协议。为避免把第一阶段监督微调和第二阶段强化学习混在一起，报告将 SFT policy 的构造、GRPO adapter 的训练以及最终 agent evaluation 分开说明。

本文中的 S1–S4 是四个 GRPO 方案代码名，用来同时标记 rollout 结构和 reward 设计。S1 表示 chain rollout + final execution reward，对应 chain_final；S2 在 S1 基础上加入失败路径的 executable fallback，对应 chain_executable；S3 表示 tree rollout + final execution reward 的树回传，对应 tree_final；S4 在 S3 基础上加入 executable fallback，对应 tree_executable。其中 chain 方案按同一 prompt 采样多条独立多轮轨迹并在组内估计 advantage；tree 方案在每个 SQL action 节点上分支、剪枝并把叶子或子树价值回传给父节点。Executable fallback 的 beta=0.1 只给最终失败但 SQL 可安全执行的路径提供下限奖励，不取代最终正确奖励。

1.1 模型谱系与两阶段 LoRA

第一阶段从 Qwen2.5-Coder-14B-Instruct 初始化一个监督微调 policy。后续 GRPO 实验统一使用同一个 SFT checkpoint 作为起点；该 checkpoint 对应 LoRA rank 32、alpha 64、学习率 5e-5，训练进度为 global step 300。这里的关键控制点是：S1–S4 并不是从不同 SFT 起点出发，而是共享同一个已完成监督微调的 policy。

为了让第二阶段训练只比较 GRPO 本身的差异，选定的 SFT adapter 先被合并进 14B base，形成统一的 Qwen2.5-Coder-14B-Instruct-SFT-Merged policy。tokenizer 与原始 14B 模型保持一致。因此，SFT-Merged 可以视为“14B base + SFT LoRA 效果”的固定初始 policy；进入 GRPO 后，不再重复加载第一阶段的 SFT adapter。

Qwen2.5-Coder-14B-Instruct + SFT LoRA (r=32, alpha=64, checkpoint-300) → fixed SFT-Merged policy + fresh GRPO LoRA (r=64, alpha=128, all-linear) → S1 / S2 / S3 / S4 LoRA checkpoint

第二阶段为每个 GRPO 方案单独训练一套新的 actor LoRA，rank 为 64、alpha 为 128，目标模块为 all-linear，学习率仍为 5e-5。因此，S1–S4 的比较对象是“同一 SFT policy 上训练出的不同 GRPO adapter”，而不是四个不同的全参数模型。

评测时，SFT-Merged baseline 只加载固定的 SFT policy；S1–S4 则在同一 SFT policy 上挂载各自的第二阶段 GRPO adapter。这样可以把报告中的性能差异解释为 GRPO 阶段 policy update 的结果，同时避免把第一阶段 SFT 权重差异引入比较。

1.2 SFT/GRPO 数据隔离与正式训练规模

最终的 S1 chain 正式训练按 source_uid 隔离 SFT 与 GRPO 数据。Spider train 原始池共有 7,000 个问题；选定的 Mixed-SFT 数据集包含 4,800 条训练记录，即 3,200 条 gold、1,137 条 direct trajectory 和 463 条 rewrite trajectory，对应 4,533 个唯一 source questions。训练记录数高于唯一问题数，是因为同一个 source question 可以贡献多条 trajectory record。

构建正式 GRPO 数据时，训练池排除了全部 4,533 个 SFT source_uid，得到 2,467 条 GRPO prompt，按 source question 计算的 SFT/GRPO overlap 为 0[1]。正式运行完成 275 step，train batch size 为 8，因此累计进行了 2,200 次 prompt presentation；每个 prompt 配置 rollout_n=8，对应 17,600 个 rollout slots。这里需要区分数据池规模与训练预算：GRPO 可用池为 2,467 条，实际优化过程累计消费 2,200 个 prompt instances；SFT 的 4,800 则是训练记录数，对应 4,533 个唯一问题。

上述零重叠结论特指最终 275-step 正式 S1 训练。此前用于 reward、KL、temperature、gamma 和 rollout 方案选择的短程实验沿用完整 Spider train 训练池，不应表述为同一套数据隔离实验。

1.4 Reward 与 executable fallback

需要区分算法语义和代码标识：配置名 chain_executable 表示“chain final + executable fallback”，tree_executable 表示“tree final + executable fallback”。S2 和 S4 都保留最终正确奖励及其折扣回传；executable reward 只在失败路径上提供 fallback，并不取代 final reward。

在 chain rollout 中，verifier 只在轨迹终止时给出 outcome reward RT。若第 T 轮生成语义正确的 SQL，则 RT=1；第 t 轮动作使用由该终局奖励反向折扣得到的经验动作回报，而不是把折扣值解释为环境在该轮给出的即时 reward。若整条轨迹最终失败，S1 的所有动作回报均为 0；S2 则只对能够在 SQLite 中安全、无错误执行的 SQL 动作赋予 fallback score beta=0.1。这里的“可执行”仅表示 execution.ok=True，不表示 SQL 与 gold query 语义等价。

R_T = 1, 若最终 SQL 正确；否则为 0 Q_hat(t) = gamma^(T − t) × R_T, 若轨迹最终成功 Q_hat(t) = beta, 若轨迹最终失败且当前 SQL 可执行（仅 S2） Q_hat(t) = 0, 其他情况

Executable fallback 是替代失败奖励的下限，而不是附加 bonus。因此，只要轨迹最终成功，S2 就与 S1 一样使用折扣后的正确奖励，不再额外加 beta。这避免“先生成错误但可执行 SQL、随后修正成功”的轨迹因为累加 fallback 而获得高于首轮直接正确的总回报。

在 tree rollout 中，正确节点是终止节点，其 outcome reward 为 1，因此该节点的经验动作回报也为 1。S3 对非正确的内部节点使用子节点经验回报的均值进行折扣回传，失败叶节点为 0。S4 在相同回传值与当前节点的 executable fallback 之间取最大值；因此，可执行性仍是回报下限，而不会与未来成功价值相加。

Q_hat(n) = 1, 若当前 SQL 正确 Q_hat(n) = gamma × mean[Q_hat(c)], S3 的非正确内部节点 Q_hat(n) = 0, S3 的失败叶节点 Q_hat(n) = max(gamma × mean[Q_hat(c)], beta × I_executable(n)), S4 的非正确内部节点 Q_hat(n) = beta × I_executable(n), S4 的非正确叶节点

因此，chain 与 tree 使用的是同一类终局 reward 折扣传播；区别在于 chain 沿一条已采样轨迹传播，而 tree 在每个内部节点对多个已采样子分支的回报取均值。这里没有学习 critic，也不是 GAE；gamma 用于构造供 GRPO 组内比较的经验动作回报。同一 parent state 生成的兄弟节点构成一个 GRPO 比较组，节点回报在组内进行中心化和标准化后得到 advantage。由此，tree 方案比较的是“同一数据库状态和反馈下，不同 SQL 动作的相对回报”。

从论文定位看，只用最终 verifier reward 训练 GRPO 是合理的 outcome-supervision 版本：DeepSeekMath 的 GRPO 会将同一 prompt 下多条输出的最终 reward 做组内归一化，并把得到的 advantage 分配到该输出的 token 上[2]。在二元正确/错误奖励、组内正负样本明确，尤其是 G=2 时，这种目标非常接近在线 DPO/对比学习；但普通 GRPO 仍包含 on-policy sampling、group normalization、PPO clip/KL 等机制，不能简单视为严格等同 DPO[3]。

DeepSeekMath 同时给出了 outcome-supervised 与 process-supervised GRPO。前者说明最终 reward 足以定义有效的 GRPO 训练目标，但其消融结果显示，在对应数学任务中，process supervision 优于 outcome supervision[2]。因此，该结果支持把最终 verifier reward 作为简单、可复现的基线，而不支持其优于过程奖励的结论。

DeepSeek-R1 讨论的是另一个维度：reward 的来源。在数学和代码等可验证任务中，程序化规则 verifier 可以避免额外训练神经奖励模型及其 reward hacking 风险[4]。这里的神经奖励模型包括只对完整输出进行预测评分的 outcome reward model（ORM），以及对中间推理步骤进行预测评分的 process reward model（PRM）；规则 verifier 与神经奖励模型的取舍，并不等价于 outcome supervision 与 process supervision 的取舍。

本实验使用程序化 SQL verifier 产生终局正确性奖励，再通过 chain 折扣或 tree backup 进行 credit assignment，但没有引入独立的过程奖励模型。因此，最终 SQL execution reward 是低复杂度、可审计的基线，而不是已经证明的最优 reward design；过程级奖励能否进一步改善训练仍需单独消融。此外，二元 verifier reward 可能使同组样本全部正确或全部错误，需要监控组内 reward 方差，避免 GRPO advantage 退化为零。

1.5 Tree frontier 与 beam 选择

树的根状态首先采样 branch_n=4 个 SQL。语义正确的节点在 prune_on_gold_reward=True 下立即终止；只有不正确、尚未达到最大轮数且能够构造 rewrite state 的节点进入下一层 frontier。当 frontier 超过 beam_size=2 时，beam 并非按模型 log probability 直接取 top-2，也不使用失败节点的最终 gold reward 排序，而是使用 rollout 过程中 agent 可见的执行信号计算 proxy score：

proxy(n) = +0.2 若成功解析出 SQL；否则 −2.0 +1.0 若 SQL 可执行；否则 −0.5 +0.2 若 SQL 可执行且结果不是空集

本实验设置 beam_tau=1.0 和 beam_epsilon_random=0.1。每次选择时有 10% 概率从 frontier 中均匀、无放回地随机保留 2 个节点；其余 90% 情况按照 exp(proxy(n) / tau) 对节点进行加权、无放回抽样，而不是确定性地选择最高分的两个节点。若 frontier 不超过 2 个节点，则全部保留。随机数由任务的 root_uid 派生，因此在 frontier 内容及顺序相同的条件下，beam 抽样可以复现。

每一层被保留的 2 个 parent node 都继续生成 4 个分支。于是三轮树搜索的最大 rollout slot 数为 4 + (3 − 1) × 2 × 4 = 20：首轮 4 个节点，第二轮和第三轮各最多 8 个节点。

5. Rollout 规模与搜索结构对照

三组正式训练均从 Qwen2.5-Coder-14B-Instruct-SFT-Ratio-Gold3200-D1137-R463-LR5e5-R32-Merged 起步，固定 train batch size=4、KL=0.01、PPO epoch=2、temperature=1.0、gamma=0.9、dynamic batching、remove padding、layered summon、训练步数和随机种子，并使用相同的 validation 子集与 greedy agent protocol 评测。S3 的两组实验同时改变 branch、beam 和 rollout slot 数；S1 还改变了 chain/tree rollout、reward scheme 与 advantage estimator，因此这里比较的是完整方案，不把差异单独归因于某一个参数。

需要先区分训练与推理：chain 并不是过时方案，而是当前 GRPO/RLVR 和 CoT 推理里的强基线。DeepSeekMath 与 DeepSeek-R1 的 GRPO 都采用“同一问题采样多条完整输出、用组内 reward 估计 advantage”的链式输出单位；CoT prompting、self-consistency 与 best-of-N 推理也都是围绕多条独立 reasoning chain 做采样、投票或重排。chain 的工程优势是简单、易并行、直接匹配最终答案 verifier 或 SQL execution reward，且不会引入 beam/proxy score 的额外偏置。因此，在本实验这种 max_turns=3、最终 SQL 可验证、评测使用 greedy agent protocol 的设置下，S1 chain n=8 成为默认候选是有文献和工程依据的。

tree-based GRPO/agent RL 文献支持的是另一个方向：当任务长程、多跳、工具调用昂贵或中间决策高不确定时，把共享前缀组织成树，可以在固定 token 或工具调用预算下复用公共前缀，并把叶子节点最终奖励回传为分支、步骤或 token 级 advantage。Tree-GRPO 还指出 intra-tree GRPO 与 step-level DPO 具有相同的偏好梯度结构。因此，tree 的主要理论收益不是“多采样必然更准”，而是更好的探索预算利用与 credit assignment；但这些收益依赖任务长度、branch 位置、advantage estimator 和 rollout 预算。本实验的 S3 tree-final 属于 SQL agent 的工程化 tree rollout 变体，不等同于 ICLR 2026 Tree-GRPO 的完整 intra-tree/inter-tree advantage estimator。

摘要

本页以时间瓶颈为主线，并在对应阶段报告显存与 CPU 内存证据。历史 S3、KL=0.01、PPO epoch=2 日志曾显示 Actor→vLLM 同步耗时 44.3 秒，但该结果来自 full-summon CPU-offload fallback，不代表当前 layered summon 成本；资源日志也显示该 fallback 伴随接近 470GB 的 CPU 内存压力。以 layered summon 成功的 5-step 运行作为当前同步路径 baseline 后，策略优化成为最主要的稳定开销；开启 dynamic_bsz 与 remove_padding 后，策略优化耗时下降约 88.1%，整卡显存峰值仍在约 59.9GB。继续提高 rollout 并发容量到 max_num_seqs=8、max_num_batched_tokens=8192 后，rollout 耗时进一步下降约 26.7%，平均 step 耗时下降约 18.7%，且没有推高整卡显存峰值。

1. 研究问题

性能测试首先要回答的是：在固定 S3 tree GRPO、KL=0.01、PPO epoch=2、4×H100 与 LoRA 训练栈下，单个 verl step 的主要时间开销究竟来自哪里，以及这些优化是否仍落在 H100 显存和主机内存预算内。具体而言，本页区分历史 full-summon CPU-offload fallback 与当前 layered summon 路径，分别评估 Actor→vLLM 同步、rollout、old/reference log-prob 和策略优化的贡献；随后只测试我们能直接控制的配置，包括 micro batch、dynamic batching、remove padding、token cap 与 vLLM rollout 容量上限。该实验的目的不是细分底层通信或内核实现，而是为正式 GRPO 训练选择更快、容量可行且可复现的默认配置。

2. 方法

分析对象为 S3 tree rollout 的 KL=0.01、PPO epoch=2 训练日志。policy 仍由 SFT-Merged 14B base 和 fresh GRPO LoRA（rank=64、alpha=128、all-linear）组成，actor 学习率为 5e-5。该运行使用 4 张 H100，训练 batch size 为 2，rollout slot 数为 20，并设置 branch_n=4、beam_size=2、max_turns=3。KL 通过 use_kl_loss=True 引入，actor 参数与优化器不 offload。

项目锁定的 verl@f663282 在检测到 actor lora_rank=64 后设置 ref_in_actor=True，不会创建独立 reference worker。trainer 的 _compute_ref_log_prob() 转而调用 actor worker，并传入 no_lora_adapter=True；worker 在 disable_adapter() 上下文中执行真实的 no-grad forward，从而以 SFT-Merged base 作为 reference policy。虽然启动脚本仍传入 REF_PARAM_OFFLOAD=True，该配置没有一份独立 reference model 可供 offload，因此不能把本次运行描述为“CPU-offloaded reference”。

历史日志中共提取到 22 个完整 timing step。为降低初始化、图编译和缓存预热的影响，统计时去掉前 5 个 warmup step，对剩余 17 个 step 分别计算总耗时，以及 gen、old_log_prob、ref、update_actor 和 update_weights 的均值、最小值与最大值。报告将原始字段 update_actor 称为“策略优化”，将 update_weights 称为“Actor→vLLM 同步”。历史日志只用于解释 fallback 瓶颈，不作为后续参数实验的 baseline。

训练侧参数实验改用 layered summon 成功的短运行作为 baseline。该 baseline 固定 ppo_micro_batch_size_per_gpu=1、LOG_PROB_USE_DYNAMIC_BSZ=False、MODEL_USE_REMOVE_PADDING=False，完成 5 个 step 且无 fallback。三个候选实验保持 S3 tree、KL=0.01、PPO epoch=2、batch size=2、rollout slot=20、branch_n=4、beam_size=2、max_turns=3 和 layered summon 不变；候选 A 仅将 micro batch 提高到 2，候选 B 开启 dynamic batching 与 remove padding 并使用 ppo_max_token_len_per_gpu=16384，候选 C 在候选 B 的基础上只把 token cap 提高到 32768。候选日志各跑 10 step，并去掉前 2 step warmup 后统计剩余 8 step。

rollout 并发实验继续从训练侧最优解出发：固定 dynamic_bsz=True、remove_padding=True、KL=0.01、PPO epoch=2 与 layered summon，只改变 vLLM rollout 侧的容量上限。baseline 使用 max_num_seqs=4、max_num_batched_tokens=4096；候选同时提高到 max_num_seqs=8、max_num_batched_tokens=8192。两组各跑 10 step，并去掉前 2 step warmup 后统计剩余 8 step。

4.1 问题

在固定 4×H100、train batch size=4、KL=0.01、PPO epoch=2、dynamic batching、remove padding 与 layered summon 的 rollout 对照实验中，S3 branch=4/beam=2/rollout_n=20 和 S1 rollout_n=8 均完成 100 step；S3 branch=8/beam=1/rollout_n=24 的初始运行则在完成第 32 step 后失败。异常栈停在 checkpoint_manager.update_weights → rollout.resume(tags=["weights"]) → vLLM wake_up → CuMem create_and_map，因此这不是 vLLM 动态生成阶段的 KV-cache OOM，也不是 actor forward/backward 内核直接 OOM，而是 actor 更新结束后、vLLM 重新映射 sleeping weight buffers 时发生的阶段边界 OOM。加入唤醒前 actor cache 清理后，同一 n=24 配置已完成 100 step，因而该故障现在同时具备失败日志和修复复跑证据。

4.2 分析方法

分析首先对齐三份日志的共同配置和前 32 个完整 step，比较 perf/total_num_tokens、global_seqlen/balanced_max、response/aborted_ratio、timing_s/update_actor 与 actor allocated/reserved 高水位；随后用 GPU_MONITOR 区分 rollout/generation、actor update 和 Actor→vLLM 同步阶段。最后核对项目锁定的 verl@f663282 源码：每个训练 batch 在 backward 前清梯度，FSDP train-mode 在整个 PPO update 退出时再次调用 optimizer_zero_grad()。因此 attention 中间量、activation、计算图和最后一次梯度在权重同步前都已失效；仍需长期保留的是模型参数、LoRA 参数、优化器状态以及 FSDP/NCCL 固定 buffer。

4.3 根因

rollout_n=24 首先提高了 actor 训练压力。与 S3 n=20 相比，初始 n=24 组的平均 token 数增加 23.6%，actor update 时间增加约 27.5%；其未 aborted 的 response 槽比例由约 36.9% 提高到 54.9%，因此变化不只是名义槽位数增加 20%。更关键的是第 33 个数据 batch：S3 n=20 在该 step 达到 49,190 tokens、每卡平衡后 12,298 tokens，actor reserved 高水位从 42.14GiB 跳到 50.52GiB，但仍勉强完成；S1 同一位置达到 47,716 tokens 和 49.84GiB reserved，也完成同步。初始 n=24 运行在写出第 33 step 指标之前失败，因此日志中的 44.21GiB reserved 只是第 32 step 的旧高水位，不能代表故障瞬间的 actor 状态。

修复复跑补全了缺失的第 33 step 数据：该 step 实际达到 61,558 tokens，未平衡最长 rank 为 31,884 tokens，每卡平衡后为 15,394 tokens；actor allocated/reserved 高水位分别达到 52.37/57.54GiB，update_actor 为 26.77 秒。尽管这一步比原先从失败日志推断的压力更高，update_weights 仍在 6.16 秒内完成，训练随后继续到 step 100。这说明 n=24 的训练峰值确实很高，但只要在权重唤醒前归还无用 allocator cache，固定 actor 状态和 vLLM 权重仍可在 80GB H100 上共存。

第一组在 rollout/generation 阶段约使用 59.6/81.6GB，确实还剩约 20GB；但第 33 step 的训练同步峰值实际接近 76.0GB，只剩约 5.5GB。失败组 OOM 前约使用 74.5GB，剩余约 7GB，无法再容纳 vLLM TP4 的固定权重 shard 及映射开销。max_num_seqs=8 和 max_num_batched_tokens=8192 只约束生成阶段的调度并发与 KV cache，不改变 wake_up(weights) 所需的固定权重映射容量。

综合三组结果，根因是：n=24 的较高训练峰值扩大了 PyTorch CUDA allocator 的 reserved cache；activation、attention 中间量和梯度虽然在语义上已经作废，但对应空闲 block 没有立即归还给 CUDA。随后 layered summon 进入固定大小的 vLLM 权重唤醒，跨进程可用物理显存不足，最终在 CuMem create_and_map 处 OOM。换言之，rollout_n=24 是训练侧高水位的触发因素，vLLM wake-up 是显存冲突实际暴露的位置。

4.4 修复与验证

提交 1ba45c38 在调用原始 update_weights()、即 vLLM 权重唤醒之前执行当前 actor rank 的 empty_cache()，将未被活跃 tensor 占用的 allocator cache 归还给 CUDA。单独把 gpu_memory_utilization 从 0.32 降到 0.20 的运行仍在第 33 step 边界 OOM；保持 0.20 和其他关键训练配置不变、加入 cache fix 后，运行以 EXIT_CODE 0 完成 100 step，总 wall time 为 4,964 秒。这个前后对照验证了缓存清理是解决本次 OOM 的关键改动，不需要降低 rollout 数或训练 token cap。后续容量实验仍应记录清理前后的逐 rank memory_allocated、memory_reserved 与 mem_get_info，用于量化实际归还的显存，而不是仅依赖 10 秒粒度的 GPU_MONITOR 峰值。

5. 结论

时间与资源证据合并后，当前瓶颈结论不再是“同步瓶颈”，而是“策略优化和 rollout 共同主导”。历史 44 秒 Actor→vLLM 同步来自 full-summon CPU-offload fallback；layered summon 成功后，同步耗时降到约 7 秒，并避免了接近 470GB CPU 内存的 fallback 路径。micro batch 提高到 2 后，PPO actor update 和 old log-prob 计算都受益，因为固定 micro-batch split 次数减少；dynamic batching 与 remove padding 的收益更大，因为它按 token budget 重新打包样本，并避免模型在 padding token 上做无效 forward/backward。

正式训练采用 dynamic_bsz=True、remove_padding=True、max_num_seqs=8 与 max_num_batched_tokens=8192。该组合先把策略优化从 30.864 秒降至 3.670 秒，再把 rollout 从 24.558 秒降至 18.000 秒；最终 10-step profiling 的平均 step 为 28.629 秒。资源上，actor/update 与 rollout 容量实验的整卡峰值保持在约 59.6–59.9GB，适合 80GB H100；ppo_max_token_len_per_gpu=32768 已验证容量可行，并在一次短 profiling 中取得更低端到端 step time，但加速主要来自 rollout 波动而不是 actor update 下降，因此默认配置仍保守使用 16384，并将 32768 保留为可切换候选。

6. 当前性能最优配置

  • 固定 workload：该性能配置对应当前 S3 tree GRPO 负载，train_batch_size=2，rollout_n=20，branch_n=4，beam_size=2，max_turns=3，4×H100。
  • Actor→vLLM 同步：使用 layered summon，同步 LoRA adapter tensor，避免 full-summon CPU-offload fallback；该路径将同步耗时从历史 fallback 的 44 秒级降到约 7 秒。
  • Actor/log-prob 训练侧：开启 activation checkpointing、dynamic_bsz=True 与 remove_padding=True；保留 ppo_mini_batch_size=2、ppo_micro_batch_size_per_gpu=1、ppo_max_token_len_per_gpu=16384。
  • vLLM rollout 侧：使用 tensor_parallel_size=4、pipeline_parallel_size=1、gpu_memory_utilization=0.32，并将容量上限设为 max_num_seqs=8、max_num_batched_tokens=8192。
  • 可切换候选：固定 micro batch 提到 2 有收益，但弱于 dynamic token packing；ppo_max_token_len_per_gpu=32768 已验证容量可行，短 profiling 中端到端更快，但该差异主要来自 rollout 波动，不能直接归因于 token cap，因此默认仍用 16384。
  • 容量守门：保留 GPU_MONITOR 与 actor perf 指标；当前组合的整卡显存峰值约 59.6–59.9GB，适合 80GB H100。

vLLM Tensor Parallel 扩展与固定 GPU 预算实验

1. 研究问题

本实验研究 Qwen2.5-Coder-14B rollout policy 在 vLLM 中采用不同 tensor parallel size 时的性能与容量权衡。第一组实验保持单个 vLLM 实例不变，比较 TP=1、TP=2 与 TP=4，回答增加模型并行度能否降低单请求和并发请求的生成延迟，以及跨卡通信开销、KV cache 容量和每卡显存如何随 TP 变化。该组用于刻画单实例的模型并行扩展性，不将 TP=4 使用更多 GPU 后得到的总吞吐直接解释为资源效率提升。

第二组实验固定 4 张 H100 的总 GPU 预算，比较 4 replicas × TP=1、2 replicas × TP=2 与 1 replica × TP=4。该组回答在相同硬件成本下，应优先使用更高 TP 降低单实例延迟，还是使用更多低 TP 副本提高聚合吞吐；同时考察多轮 SQL agent rollout 中长短请求不均衡造成的尾延迟和批次完成时间。最终目标是为 verl/Ray rollout worker 选择吞吐、延迟、显存和调度复杂度之间更合适的部署方式。

2. 方法

2.1 Workload 与控制变量

实验使用与 GRPO rollout 相同的 Qwen2.5-Coder-14B policy、tokenizer、精度和生成协议，并在同一台 4×H100 节点上完成。固定 vLLM 版本、CUDA/NCCL 环境、模型 checkpoint、max_model_len、采样参数、请求集合与随机种子；除 TP 和副本数外，不改变影响调度与显存容量的参数。请求从真实 SQL agent rollout 中构造固定 trace，保留输入长度、输出长度和交互轮数分布，并覆盖并发度 1/2/4/8。每个配置先完成独立 warmup，再重复测量相同 trace；若某配置发生 OOM，则记录其容量边界，不通过缩短上下文或降低并发改变该配置的 workload。
