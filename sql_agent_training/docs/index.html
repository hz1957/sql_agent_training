Qwen2.5-Coder-14B-Instruct · Pure SFT vs. Mixed SFT

单轮监督与轨迹混合监督的对照实验

实验记录

摘要

本研究比较从同一原始 Qwen2.5-Coder-14B-Instruct 出发的参数高效监督微调策略，并重点考察执行验证轨迹在 SQL agent 协议中的作用。第一步直接比较 Pure-SFT 与 Mixed-SFT：在同一组 500 条 Spider validation 样本上，Pure-SFT checkpoint-300 的 execution accuracy 为 77.60%，Mixed-SFT checkpoint-300 为 80.60%，绝对差异为 +3.00 个百分点。第二步固定 Mixed-SFT 数据，进行学习率与 LoRA rank 网格；lr=5e-5, r=32 仍为最高点估计，扩大到 r=64 未带来稳定收益。第三步固定 lr=5e-5, r=32、4,800 条训练记录与 300 optimizer steps，比较 gold SQL 与 trajectory supervision 的比例；3,200 gold + 1,600 trajectory 取得最高 execution accuracy 79.80%，相对 4,800 gold-only 的 76.40% 提高 +3.40 个百分点。整体结果支持在单轮 gold SQL 监督中混入约三分之一执行验证轨迹，但现有结论仍基于单一训练 seed 与 500-sample validation subset。

研究问题

本实验旨在回答三个问题。第一，在 SQL agent 的执行反馈评测协议下，相较于仅使用单轮 question/schema-to-SQL 样本的 Pure-SFT，引入经执行验证的 trajectory supervision 是否能够在控制模型起点、LoRA 容量、学习率、训练预算与解码协议后带来可观测的 execution accuracy 增益。第二，在 Mixed-SFT 已显示正向点估计后，学习率与 LoRA rank 的有限网格是否改变主候选配置。第三，在固定总训练记录数与优化预算的条件下，gold SQL 与 trajectory supervision 的混合比例如何影响最终执行正确率、rewrite 行为与耗尽交互轮数的比例。

1. 第一步：Pure-SFT 与 Mixed-SFT 对照

第一步检验的核心假设是：在相同原始 14B 起点、LoRA 容量、学习率、global batch size 与 300-step 训练预算下，以经执行验证的 agent trajectory 替换一部分单轮 gold SQL，能否提高模型在多轮执行反馈协议下的最终 SQL 正确率。原始 14B 无 LoRA 模型仅用于刻画微调前性能；第一步的主要效应量定义为 Mixed-SFT checkpoint-300 与 Pure-SFT checkpoint-300 的配对 execution-accuracy 差异。

在相同训练预算下，Mixed-SFT 的 execution accuracy 为 80.60%，比 Pure-SFT 高 3.00 个百分点。训练过程中的最高中间评测结果为 81.00%，与最终结果仅相差 2/500 个样本，因此不作为更换最终模型的依据。

后续实验统一采用完成预设训练预算的 Mixed-SFT 模型。当前结果来自单一训练 seed 和 500 条 validation 样本，尚不足以区分 direct 与 rewrite trajectory 的独立贡献。

3.4 SFT 结论

SFT 实验整体结论如下。第一，Mixed-SFT 相对于 Pure-SFT 的点估计提升在两个独立设置中复现：第一步的 3,200 gold + 1,600 trajectory 为 80.60%，第三步同等比例在重新生成轨迹池后为 79.80%，均高于对应 gold-only 对照。第二，lr=5e-5, r=32 是当前最优且更简洁的 LoRA 配置，r=64 未显示必要性。第三，在固定总训练记录数时，约三分之一 trajectory supervision 是当前最佳比例；它比纯 gold-only 更好，同时比 50% trajectory 更稳定地降低平均交互轮数和耗尽轮数率。

Qwen2.5-Coder-14B-Instruct-SFT-Merged

GRPO 奖励方案与搜索策略实验结果

实验记录

摘要

本实验研究的是两阶段参数高效训练：首先将 Qwen2.5-Coder-14B-Instruct 的 SFT LoRA 合并进 14B 基座，形成统一的 SFT-Merged policy；随后在该 policy 上为每个 GRPO 方案训练一套新的 LoRA，而不是更新 14B 全部参数。初始 S1–S4 reward 设计对照中，S3 的执行准确率点估计最高，为 80.67%，相对 SFT-Merged baseline 提升 3.33 个百分点；随后的超参数实验确定 KL=0.01、PPO epoch=2、temperature=1.0 与 gamma=0.9。在更新后的 SFT ratio base 上，rollout 对照得到 S3 branch=4/beam=2/n=20 83.67%、S1 n=8 83.33% 和 S3 branch=8/beam=1/n=24 82.00%；准确率没有拉开清晰差距，但 S1 n=8 的计算与交互效率最好。

研究问题

本实验旨在回答：在相同 SFT-Merged base policy 与相同第二阶段 LoRA 训练框架下，不同 reward 设计与 rollout 搜索策略是否能够相对 SFT-Merged baseline 提供额外的 execution accuracy 增益；同时，S1–S4 之间的差异应如何在 reward 变量、chain/tree rollout 形式、batch size 与 PPO mini-batch size 等潜在混杂因素共同存在的条件下进行解释。

1. 方法

本节描述 GRPO 实验的比较对象、控制变量与评测协议。为避免把第一阶段监督微调和第二阶段强化学习混在一起，报告将 SFT policy 的构造、GRPO adapter 的训练以及最终 agent evaluation 分开说明。

本文中的 S1–S4 是四个 GRPO 方案代码名，用来同时标记 rollout 结构和 reward 设计。S1 表示 chain rollout + final execution reward，对应 chain_final；S2 在 S1 基础上加入失败路径的 executable fallback，对应 chain_executable；S3 表示 tree rollout + final execution reward 的树回传，对应 tree_final；S4 在 S3 基础上加入 executable fallback，对应 tree_executable。其中 chain 方案按同一 prompt 采样多条独立多轮轨迹并在组内估计 advantage；tree 方案在每个 SQL action 节点上分支、剪枝并把叶子或子树价值回传给父节点。Executable fallback 的 beta=0.1 在 tree 方案中作为失败组的辅助 advantage 权重，而不是 raw value 下限。

1.1 模型谱系与两阶段 LoRA

第一阶段从 Qwen2.5-Coder-14B-Instruct 初始化一个监督微调 policy。后续 GRPO 实验统一使用同一个 SFT checkpoint 作为起点；该 checkpoint 对应 LoRA rank 32、alpha 64、学习率 5e-5，训练进度为 global step 300。这里的关键控制点是：S1–S4 并不是从不同 SFT 起点出发，而是共享同一个已完成监督微调的 policy。

为了让第二阶段训练只比较 GRPO 本身的差异，选定的 SFT adapter 先被合并进 14B base，形成统一的 Qwen2.5-Coder-14B-Instruct-SFT-Merged policy。tokenizer 与原始 14B 模型保持一致。因此，SFT-Merged 可以视为“14B base + SFT LoRA 效果”的固定初始 policy；进入 GRPO 后，不再重复加载第一阶段的 SFT adapter。

Qwen2.5-Coder-14B-Instruct + SFT LoRA (r=32, alpha=64, checkpoint-300) → fixed SFT-Merged policy + fresh GRPO LoRA (r=64, alpha=128, all-linear) → S1 / S2 / S3 / S4 LoRA checkpoint

第二阶段为每个 GRPO 方案单独训练一套新的 actor LoRA，rank 为 64、alpha 为 128，目标模块为 all-linear，学习率仍为 5e-5。因此，S1–S4 的比较对象是“同一 SFT policy 上训练出的不同 GRPO adapter”，而不是四个不同的全参数模型。

评测时，SFT-Merged baseline 只加载固定的 SFT policy；S1–S4 则在同一 SFT policy 上挂载各自的第二阶段 GRPO adapter。这样可以把报告中的性能差异解释为 GRPO 阶段 policy update 的结果，同时避免把第一阶段 SFT 权重差异引入比较。

1.2 SFT/GRPO 数据隔离与正式训练规模

最终的 S1 chain 正式训练按 source_uid 隔离 SFT 与 GRPO 数据。Spider train 原始池共有 7,000 个问题；选定的 Mixed-SFT 数据集包含 4,800 条训练记录，即 3,200 条 gold、1,137 条 direct trajectory 和 463 条 rewrite trajectory，对应 4,533 个唯一 source questions。训练记录数高于唯一问题数，是因为同一个 source question 可以贡献多条 trajectory record。

构建正式 GRPO 数据时，训练池排除了全部 4,533 个 SFT source_uid，得到 2,467 条 GRPO prompt，按 source question 计算的 SFT/GRPO overlap 为 0[1]。正式运行完成 275 step，train batch size 为 8，因此累计进行了 2,200 次 prompt presentation；每个 prompt 配置 rollout_n=8，对应 17,600 个 rollout slots。这里需要区分数据池规模与训练预算：GRPO 可用池为 2,467 条，实际优化过程累计消费 2,200 个 prompt instances；SFT 的 4,800 则是训练记录数，对应 4,533 个唯一问题。

上述零重叠结论特指最终 275-step 正式 S1 训练。此前用于 reward、KL、temperature、gamma 和 rollout 方案选择的短程实验沿用完整 Spider train 训练池，不应表述为同一套数据隔离实验。

1.4 Reward 与 executable fallback

需要区分算法语义和代码标识：配置名 chain_executable 表示“chain final + executable fallback”，tree_executable 表示“tree final + executable fallback”。S2 和 S4 都保留最终正确奖励及其折扣回传；区别在于 S2 把可执行性写入失败轨迹的 raw score，而 S4 只在 tree sibling group 没有任何最终正确性区分时，把可执行性作为标准化后的 fallback advantage 信号。

在 chain rollout 中，verifier 只在轨迹终止时给出 outcome reward RT。若第 T 轮生成语义正确的 SQL，则 RT=1；第 t 轮动作使用由该终局奖励反向折扣得到的经验动作回报，而不是把折扣值解释为环境在该轮给出的即时 reward。若整条轨迹最终失败，S1 的所有动作回报均为 0；S2 则只对能够在 SQLite 中安全、无错误执行的 SQL 动作赋予 fallback score beta=0.1。这里的“可执行”仅表示 execution.ok=True，不表示 SQL 与 gold query 语义等价。

R_T = 1, 若最终 SQL 正确；否则为 0 Q_hat(t) = gamma^(T − t) × R_T, 若轨迹最终成功 Q_hat(t) = beta, 若轨迹最终失败且当前 SQL 可执行（仅 S2） Q_hat(t) = 0, 其他情况

在 chain S2 中，executable fallback 是替代失败奖励的下限，而不是附加 bonus。因此，只要轨迹最终成功，S2 就与 S1 一样使用折扣后的正确奖励，不再额外加 beta。这避免“先生成错误但可执行 SQL、随后修正成功”的轨迹因为累加 fallback 而获得高于首轮直接正确的总回报。

在 tree rollout 中，正确节点是终止节点，其 outcome reward 为 1，因此该节点的 correctness-backed return 也为 1。S3/S4 都先独立计算由最终正确性回传得到的 F(n)：非正确内部节点取子节点 F 的均值并乘 gamma，失败叶节点为 0。S4 不再逐节点取 max(F, beta × I_executable)；executable fallback 只在 sibling group 的最终正确性信号完全无法区分节点时，用标准化后的可执行性指标打破平局。

因此，chain 与 tree 使用的是同一类终局 reward 折扣传播；区别在于 chain 沿一条已采样轨迹传播，而 tree 在每个内部节点对多个已采样子分支的回报取均值。这里没有学习 critic，也不是 GAE；gamma 用于构造供 GRPO 组内比较的经验动作回报。同一 parent state 生成的兄弟节点构成一个 GRPO 比较组，节点回报在组内进行中心化和标准化后得到 advantage。由此，tree 方案比较的是“同一数据库状态和反馈下，不同 SQL 动作的相对回报”。

从论文定位看，只用最终 verifier reward 训练 GRPO 是合理的 outcome-supervision 版本：DeepSeekMath 的 GRPO 会将同一 prompt 下多条输出的最终 reward 做组内归一化，并把得到的 advantage 分配到该输出的 token 上[2]。在二元正确/错误奖励、组内正负样本明确，尤其是 G=2 时，这种目标非常接近在线 DPO/对比学习；但普通 GRPO 仍包含 on-policy sampling、group normalization、PPO clip/KL 等机制，不能简单视为严格等同 DPO[3]。

DeepSeekMath 同时给出了 outcome-supervised 与 process-supervised GRPO。前者说明最终 reward 足以定义有效的 GRPO 训练目标，但其消融结果显示，在对应数学任务中，process supervision 优于 outcome supervision[2]。因此，该结果支持把最终 verifier reward 作为简单、可复现的基线，而不支持其优于过程奖励的结论。

DeepSeek-R1 讨论的是另一个维度：reward 的来源。在数学和代码等可验证任务中，程序化规则 verifier 可以避免额外训练神经奖励模型及其 reward hacking 风险[4]。这里的神经奖励模型包括只对完整输出进行预测评分的 outcome reward model（ORM），以及对中间推理步骤进行预测评分的 process reward model（PRM）；规则 verifier 与神经奖励模型的取舍，并不等价于 outcome supervision 与 process supervision 的取舍。

本实验使用程序化 SQL verifier 产生终局正确性奖励，再通过 chain 折扣或 tree backup 进行 credit assignment，但没有引入独立的过程奖励模型。因此，最终 SQL execution reward 是低复杂度、可审计的基线，而不是已经证明的最优 reward design；过程级奖励能否进一步改善训练仍需单独消融。此外，二元 verifier reward 可能使同组样本全部正确或全部错误，需要监控组内 reward 方差，避免 GRPO advantage 退化为零。

1.5 Tree frontier 与 beam 选择

树的根状态首先采样 branch_n=4 个 SQL。通过 checker 的可执行节点在 prune_on_terminal_proxy=True 下立即终止；SQLite 反馈为不可恢复错误的节点也作为失败叶子剪枝，包括表不存在且与 schema 表名不构成轻微拼写差异的明显幻觉表名、timeout 和 memory limit。只有未被 proxy 终止、尚未达到最大轮数且能够构造 rewrite state 的节点进入下一层 frontier。当 frontier 超过 beam_size=2 时，beam 并非按模型 log probability 直接取 top-2，也不使用节点的最终 gold reward 排序，而是使用 rollout 过程中 agent 可见的执行信号计算 proxy score：

proxy(n) = +0.2 若成功解析出 SQL；否则 −2.0 +1.0 若 SQL 可执行；否则 −0.5 +0.2 若 SQL 可执行且结果不是空集

本实验设置 beam_tau=1.0 和 beam_epsilon_random=0.1。每次选择时有 10% 概率从 frontier 中均匀、无放回地随机保留 2 个节点；其余 90% 情况按照 exp(proxy(n) / tau) 对节点进行加权、无放回抽样，而不是确定性地选择最高分的两个节点。若 frontier 不超过 2 个节点，则全部保留。随机数由任务的 root_uid 派生，因此在 frontier 内容及顺序相同的条件下，beam 抽样可以复现。

每一层被保留的 2 个 parent node 都继续生成 4 个分支。于是三轮树搜索的最大 rollout slot 数为 4 + (3 − 1) × 2 × 4 = 20：首轮 4 个节点，第二轮和第三轮各最多 8 个节点。

三组正式训练均从 Qwen2.5-Coder-14B-Instruct-SFT-Ratio-Gold3200-D1137-R463-LR5e5-R32-Merged 起步，固定 train batch size=4、KL=0.01、PPO epoch=2、temperature=1.0、gamma=0.9、dynamic batching、remove padding、layered summon、训练步数和随机种子，并使用相同的 validation 子集与 greedy agent protocol 评测。S3 的两组实验同时改变 branch、beam 和 rollout slot 数；S1 还改变了 chain/tree rollout、reward scheme 与 advantage estimator，因此这里比较的是完整方案，不把差异单独归因于某一个参数。

需要先区分训练与推理：chain 并不是过时方案，而是当前 GRPO/RLVR 和 CoT 推理里的强基线。DeepSeekMath 与 DeepSeek-R1 的 GRPO 都采用“同一问题采样多条完整输出、用组内 reward 估计 advantage”的链式输出单位；CoT prompting、self-consistency 与 best-of-N 推理也都是围绕多条独立 reasoning chain 做采样、投票或重排。chain 的工程优势是简单、易并行、直接匹配最终答案 verifier 或 SQL execution reward，且不会引入 beam/proxy score 的额外偏置。因此，在本实验这种 max_turns=3、最终 SQL 可验证、评测使用 greedy agent protocol 的设置下，S1 chain n=8 成为默认候选是有文献和工程依据的。

tree-based GRPO/agent RL 文献支持的是另一个方向：当任务长程、多跳、工具调用昂贵或中间决策高不确定时，把共享前缀组织成树，可以在固定 token 或工具调用预算下复用公共前缀，并把叶子节点最终奖励回传为分支、步骤或 token 级 advantage。Tree-GRPO 还指出 intra-tree GRPO 与 step-level DPO 具有相同的偏好梯度结构。因此，tree 的主要理论收益不是“多采样必然更准”，而是更好的探索预算利用与 credit assignment；但这些收益依赖任务长度、branch 位置、advantage estimator 和 rollout 预算。本实验的 S3 tree-final 属于 SQL agent 的工程化 tree rollout 变体，不等同于 ICLR 2026 Tree-GRPO 的完整 intra-tree/inter-tree advantage estimator。

5. 结论与限制

500-sample 配对结果支持两个克制结论。第一，S3 相对 SFT 出现 29 次“由错误变正确”和 16 次“由正确变错误”，但 exact McNemar 尚未跨过 0.05。第二，S3 与 S1 的独占正确数量接近，没有显示稳定的策略差异；结合主实验的资源结果，S1 仍是更便宜的默认方案。

误差案例进一步表明，下一阶段最有价值的改进点不是单纯扩大 rollout，而是提升 checker 的精度与轨迹状态管理：在错误 SQL 上过早接受、对正确 SQL 反复拒绝、以及缺少 best-so-far 回滚，都会吞掉 policy 已具备的 SQL 能力。本页的分析范围限定为最终输出与选中轨迹，不对 tree search 的内部候选分支过程作进一步归因。

GRPO 训练与 Rollout 性能分析

Pipeline profiling

定位 GRPO/verl 瓶颈

摘要

历史 full-summon CPU-offload 路径的 Actor→vLLM 同步耗时为 44.3 秒，CPU 内存接近 470GB。改用 layered summon 后，同步耗时为 7.2 秒，单卡显存峰值约 59.9GB。开启 dynamic_bsz 与 remove_padding 后，策略优化耗时从 30.864 秒降至 3.670 秒。将 rollout 容量从 seqs=4/tokens=4096 提高到 seqs=8/tokens=8192 后，rollout 耗时从 24.558 秒降至 18.000 秒，平均 step 从 35.225 秒降至 28.629 秒。

1. 研究问题

在固定 S3 tree GRPO、KL=0.01、PPO epoch=2、4×H100 与 LoRA 训练栈下，测量 rollout、old/reference log-prob、策略优化和 Actor→vLLM 同步耗时。参数实验比较 micro batch、dynamic batching、remove padding、token cap 与 vLLM rollout 容量，并记录 GPU 与 CPU 内存峰值。

2. 方法

分析对象为 S3 tree rollout 的 KL=0.01、PPO epoch=2 训练日志。policy 仍由 SFT-Merged 14B base 和 fresh GRPO LoRA（rank=64、alpha=128、all-linear）组成，actor 学习率为 5e-5。该运行使用 4 张 H100，训练 batch size 为 2，rollout slot 数为 20，并设置 branch_n=4、beam_size=2、max_turns=3。KL 通过 use_kl_loss=True 引入，actor 参数与优化器不 offload。

4. Rollout n=24 显存 OOM 诊断

4.1 问题

OOM 链路为：n=24 batch 提高 actor 显存峰值；PyTorch allocator 保留已空闲的 reserved block；vLLM wake-up 重新映射权重时物理显存不足；CuMem create_and_map 失败。

vLLM Tensor Parallel 扩展与固定 GPU 预算实验

摘要

本实验在同一台 4×H100 节点上，使用相同的 300 条 SQL agent validation prompt，对 Qwen2.5-Coder-14B policy 的 vLLM tensor parallel 配置进行对照。全局并发度 8 的单次运行中，固定四卡预算下 1×TP=4 达到 31.15 requests/s。后续在全局并发度 32 与 64 下，对 4×TP=1、2×TP=2 和 1×TP=4 各重复 3 次：并发度 32 时三者分别为 63.76±0.50、71.22±0.25 和 59.91±0.22 requests/s；并发度 64 时分别为 96.62±0.65、95.08±2.14 和 81.50±3.15 requests/s。18 次高并发运行共完成 5,400/5,400 个请求，无请求失败或 OOM。以上数据来自不包含 SQL 执行反馈与 rewrite turn 的单轮生成 workload。

1. 研究问题

第一组保持单个 vLLM 实例不变，比较 TP=1、TP=2 与 TP=4 的请求吞吐、生成延迟和每 GPU 吞吐。第二组固定 4 张 H100，比较 4 replicas × TP=1、2 replicas × TP=2 与 1 replica × TP=4，并将全局并发度从 8 提高到 32 和 64，记录拓扑排序是否随请求压力变化。服务启动、SQL 执行和 agent rewrite 不计入本轮测量窗口。

吞吐指标包括 output tokens/s、total tokens/s 与 requests/s；延迟指标包括 TTFT、TPOT 和端到端 request latency，并报告 mean、p50、p95 与 p99。资源指标来自 nvidia-smi 采样。并发度 8 的结果为单次运行；并发度 32/64 的结果为 3 次运行的算术均值，吞吐同时报告样本标准差。表中的 p50、p95、p99、TTFT、TPOT 与峰值显存均为三个 run-level 指标的均值，不是合并 900 个请求后重新计算的分位数。
