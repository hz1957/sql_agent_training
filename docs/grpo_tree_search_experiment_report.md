# GRPO Agent Training Experiment Report: Tree Search vs. Chain

## 1. 实验背景与实验组设置
本次实验旨在探索不同生成策略（纯线性 Chain vs. 树状探索 Tree Search）以及不同奖励粒度（仅最终奖励 Final vs. 带有中间执行反馈 Executable）对大模型（Qwen25-Coder-14B）强化学习能力的提升效果。

实验包含四个对比组（S1 - S4）：
- **S1 (Chain Final)**: 朴素的线性生成，仅在多轮交互结束时给予最终奖励。
- **S2 (Chain Executable)**: 线性生成，在每轮执行结束后给予中间的可执行状态反馈奖励。
- **S3 (Tree Final)**: 树搜索生成（分支数为4，束搜索为2），仅在叶子节点/终止节点给予最终奖励。
- **S4 (Tree Executable)**: 树搜索生成，并在树节点的每一步提供中间的执行状态反馈奖励。

## 2. 训练过程中的挑战与突破

在早期的训练调试中，我们遇到并成功解决了两个导致训练瘫痪的严重问题：

### 2.1 PPO_KL 归零与 Advantage 崩溃问题 (S1 / S2)
**症状**：在初始配置（`ROLLOUT_N=4`）下，模型在 100 步左右发生策略停滞，`actor/ppo_kl` 长期归零，且 `actor/loss` 趋近于零（如 `-1.49e-08`）。
**根因分析**：在 GRPO 算法中，需要同组内的多个样本进行优劣对比来计算 Advantage。当 `ROLLOUT_N` 太小（如为 4）时，4个采样的结果往往同对或同错，导致平均值被减去后 Advantage 全体归零，梯度彻底消失。
**解决方案**：将 S1 和 S2 的 `ROLLOUT_N` 从 4 提升到 8，保证了同批次采样内的分数方差。修改后，S1 和 S2 重新焕发活力，训练分数大幅攀升（部分 batch 得分突破 1.5）。

### 2.2 树搜索导致的 CPU 内存泄漏 (S3 / S4)
**症状**：由于树搜索节点呈指数级爆炸，原始 Batch Size 配置导致主节点 CPU 内存飙升至 ~470 GB，逼近 OOM 崩溃边缘。
**解决方案**：果断将 S3 和 S4 的 `TRAIN_BATCH_SIZE` 从 8 降至 2。这不仅完美地将 CPU 内存占用稳定在 ~150 GB，还维持了与 S1/S2 相近的单步训练耗时（~95s），确保了严格的对照实验环境。

## 3. 评估结果分析 (Global Step 100)

在 Step 100 产生的 Checkpoint 上运行 Spider Eval 评估，得到以下核心指标：

| 模型版本 | 核心策略 | 执行准确率 (Execution Accuracy) | 重写成功率 (Rewrite Success Rate) | 平均轮数 (Avg Turns) |
| :--- | :--- | :--- | :--- | :--- |
| **🥇 S3** | Tree Search + Final | **80.66%** | **62.20%** | **1.76** |
| **🥈 S1** | Chain + Final | 80.33% | 56.47% | 1.47 |
| **🥉 S2** | Chain + Executable | 79.66% | 54.54% | 1.44 |
| **4️⃣ S4** | Tree Search + Executable | 76.00% | 52.25% | 1.66 |

## 4. 核心洞察与发现

### 4.1 Tree Search 赋予了模型极强的“自我纠错 (Self-Correction)”能力
- 数据显示，**S3 取得了全场最高的准确率 (80.66%) 和最高的重写成功率 (62.20%)**。
- 这意味着，当 S3 的初次 SQL 生成发生错误时，它在后续的 debug 修改中有超过六成的概率能够化险为夷。其较高的平均轮数（1.76）证明了模型极大地利用了多轮反思的机制，**树搜索赋予了模型在碰壁时退回上一步寻找其他可能性的超强能力**。

### 4.2 奖励介入过早导致“短视” (Credit Assignment Bias)
- 带有每步 Executable 反馈的实验组（S2: 79.66%, S4: 76.00%）反而在准确率上不如它们的基线（S1: 80.33%, S3: 80.66%）。
- **分析**：这在强化学习中非常典型。过于严苛或早期的中间反馈可能会过度惩罚那些“只有一点微小语法错误，但整体思路完全正确”的分支，导致这些有潜力的高质量推理树被过早剪枝。给予模型充分探索空间的 Final 奖励机制，反而更能孕育出全局最优解。

### 4.3 PPO 训练中不要盲信 Training Score
- 训练日志中偶尔出现的极低分数（如 S3 在 step 150 时均分为 0.31），纯粹是由 mini-batch 抽样的难度波动引起的。
- 真正可靠的指标永远是固定的 Eval 测试集上的执行准确率。这警示我们在大模型 RL 训练中，必须建立完善的流水线化的 Eval 机制。

## 5. 后续实验建议
1. **测试首尾 Checkpoint**：建议继续跑出 S1-S4 在 **Step 50** 和 **Step 150** 的 Eval 成绩。借此观察模型在后期是否存在过度拟合导致能力退化（Mode Collapse/Reward Hacking）。
2. **重点深挖 S3**：S3 的潜力巨大，如果算力充足，可以在最终发布的 Paper 中重点突出 S3 (Tree Search) 机制带来的 Self-correction 增益。
